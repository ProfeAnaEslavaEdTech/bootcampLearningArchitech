# PART A — OPERATIVE SPECIFICATION

## A.1 Identity and purpose
- **Real id:** `juez`. Component no. 3 of the real inventory (Alex, 1 Sep 2026).
- **Function:** validate each tip or correction generated by the Corrector **before** it is shown to the student. Acts as a pedagogical quality filter: rejects false, ambiguous, or level-inappropriate tips.
- **What it is NOT:** not the tip generator (that is the Corrector), does not evaluate the student's production for the band, does not emit measurement evidence.
- **Critical status:** the Judge's prompt has **never been documented** in the agent registry. False tips have passed the filter (active finding). No own LRS trace.

## A.2 Model (fixed)
- Free tier with verified NO-TRAIN contract.
- **CRITICAL GAP:** model and prompt version are NOT declared in the registry. The Judge's prompt is unknown to the governance system.

## A.3 Mounted knowledge (by code)
- Unknown (prompt not documented).
- **Minimum required:** registry v0.8.3 + working level + the tip to validate.

## A.4 Inputs (expected contract)
| RECEIVES | MUST NEVER RECEIVE |
|---|---|
| Tip generated by the Corrector | The student's declared level |
| Working level (±1) | Band, evidence, measurement result |
| Student's turn (context) | Real student or company data |

## A.5 Expected output
- Binary: `{valid: true/false, reason?: string}`.
- If `valid: false`, the tip is discarded and the Corrector regenerates.
- Today: no evidence that the rejection works correctly (false tips have passed).

## A.6 xAPI emission
- **None of its own.** The Judge is an internal component of the Corrector flow; its decisions do not generate direct xAPI statements.
- If rejections are to be recorded, they are emitted from the Corrector's code with `agent-id=juez` as context.

## A.7 Governance guardrails
- **G-NIVEL-1:** must not know the declared level or the band.
- **No own statement → no scoring-firewall risk.**
- **Active risk:** false tips are passing the filter → the Judge is not fulfilling its governance function.
- **N3 blocked:** without a documented prompt, the hash test cannot be implemented.

## A.8 Explicit prohibitions
✗ Approving a tip that contradicts the inventory · ✗ Approving a tip inappropriate for the level · ✗ Emitting bands · ✗ Generating new content (validates only) · ✗ Reproducing text from commercial PDFs.

## A.9 Incidents it opens (via code)
- `incident/tip-rejected` — tip rejected by the Judge; Corrector regenerates.
- `incident/false-tip-approved` — false tip approved and shown to the student (active finding, D13 pending).

## A.10 Admission and deployment tests
- **A1 (blocked):** 20 false tips → 100% rejected. Blocked until the prompt is documented.
- **A2:** 20 correct tips → 100% approved (no false negatives).
- **N3:** production prompt == approved. Blocked (no documented prompt).

## A.11 Versioning
Validation criterion change = version bump + signature + map update. **Today: versioning impossible without a documented prompt.**
