The Structural Difference: B2C vs. B2B Tracking

B2C — Individual Consumers
  • User buys course with personal email (user@gmail.com)
  • LRS tracks individual progress, certifications, achievements
  • Data used for personal portfolio + marketing analytics
  • Traffic: predictable, steady stream
B2B — Corporate Clients
  • Company buys 500 seat licences for its employees
  • LRS must segment data so HR sees only their employees
  • Data strictly isolated from other businesses
  • Traffic: sudden spikes (e.g. 5,000 users by Friday)
The key shift: B2C is about the individual learner. B2B is about the organisation — and the organisation owns the right to see its employees' data without seeing anyone else's.

Four Architecture Requirements

1. Multi-Tenancy (Critical for B2B)

Your LRS must use virtual walls to separate data. Each corporate client gets an isolated Tenant Account at its own endpoint — e.g. yourlrs.com/company-a/ — with its own unique API Key and Secret. Company A's admins can never query Company B's data.

2. Advanced Actor Identification

B2C actors: identified by personal email → mailto:john@gmail.com
B2B actors: must include corporate identifiers (account IDs, enterprise OpenIDs) so statements map cleanly to their employer's tenant roster.

3. Strict Permission Scoping (xAPI Scopes)

RoleScope GrantedEffect
B2C Userstatements/write:ownCan only post their own data
B2B Client Managerstatements/read (filtered)Read-only, hard-filtered to their Organisation ID
Platform AdminFull scopeGlobal access across all tenants

4. Auto-Scaling Ingestion

Your ingestion endpoint must auto-scale elastically to handle B2B corporate bursts without dropping B2C statement packets that arrive concurrently.

B2B Delivery: Scenario A vs. Scenario B

Scenario A — Client Dashboard (SMB)

Target: small-to-medium businesses without an internal LRS. They want a turnkey login to see their employees' data.

  • You provision a client admin account in your multi-tenant LRS
  • Scope: statements/read permanently filtered to their Organisation ID
  • They see: progress, test scores, video viewing — nothing from other tenants
  • Often white-labeled with their brand
  • Monetisation: included in standard business packages

Scenario B — Statement Forwarding / "Firehose" (Enterprise)

Target: Fortune 500s, government agencies, institutions that already own Cornerstone, Moodle, Canvas, Watershed, or their own LRS.

  • Client provides: their LRS Endpoint URL + API Key + API Secret
  • You configure a Forwarding Rule in your master LRS
  • Every statement matching that client's tenant ID is instantly replicated via HTTPS POST to their endpoint
  • No manual exports. No CSV. Real-time, automatic
  • Monetisation: premium tier or integration fee — justified by the infrastructure cost
Competitive advantage: offering both Scenario A and Scenario B removes the most common enterprise sales objection — "we can't give our data to an external platform."

Implementation Phase 1: Dynamic xAPI Statement

For custom UI interactions (video events, React quiz components, page-view tracking), your frontend must inject the tenant_id into the statement's context.extensions.

function sendCustomXAPIStatement(user, activityId, verbId, verbDisplay) {
  const statement = {
    "actor": {
      "name":  user.name,
      "mbox":  `mailto:${user.email}`
    },
    "verb": {
      "id":      `http://adlnet.gov${verbId}`,
      "display": { "en-US": verbDisplay }
    },
    "object": {
      "id": `https://yourmarketplace.com${activityId}`
    },
    "context": {
      "extensions": {
        // ← This is what your LRS reads to route to the right tenant
        "https://yourmarketplace.com/tenant": user.tenant_id
      }
    }
  };

  // Never call LRS directly from frontend — route via your backend API
  return fetch('/api/lrs/statements', {
    method:  'POST',
    headers: { 'Content-Type': 'application/json' },
    body:    JSON.stringify(statement)
  });
}
Security note: the frontend never holds LRS API keys. It sends statements to /api/lrs/statements — your backend validates the session, resolves the tenant_id, injects the correct credentials, and forwards to the LRS. The client browser never touches the LRS directly.

Implementation Phase 2: Dynamic Articulate Launch

Articulate Storyline/Rise packages published as cmi5 or xAPI accept LRS credentials via URL parameters at launch time. This means one course file works for every tenant — no duplicate builds.

// B2C user — global LRS credentials
https://yourmarketplace.com/courses/course-id/index.html
  ?endpoint=https://yourlrs.com/b2c/
  &auth=Basic BASE64_B2C_KEY_SECRET
  &actor={"name":"Jane Smith","mbox":"mailto:jane@gmail.com"}

// B2B user — tenant-specific credentials injected dynamically
https://yourmarketplace.com/courses/course-id/index.html
  ?endpoint=https://yourlrs.com/tenant_company_abc/
  &auth=Basic BASE64_COMPANY_ABC_KEY
  &actor={"name":"John Doe","mbox":"mailto:john@company.com"}

Articulate reads these URL parameters on initialisation, connects to the correct LRS tenant, and streams all slide views, quiz scores, and completions directly into the right bucket — automatically.

The operational rule: your backend resolves account_type → if B2B, substitutes DYNAMIC_TENANT_ID and DYNAMIC_BASE64_KEY from a server-side tenant config map → builds the iframe src → client browser launches the course. The course file itself is identical for every user.

A prospect asks three questions during a sales call. Answer out loud before revealing.

(a) "We have 300 employees. Our HR director wants to log in on Friday afternoons and see who completed what."

Reveal recommendation (+10 XP)

Reveal recommendation (+10 XP)

(c) "We sell to both consumers online and to corporations. Can one platform handle both?"

Reveal recommendation (+10 XP)

Yes — this is the B2X model. Route B2C users to a global tenant with aggregated analytics. Route each B2B corporate client to their own isolated tenant.
