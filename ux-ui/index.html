Module 2 · Wireframing for L&D

Lo-fi to hi-fi — wireframing eLearning interactions

Three canonical eLearning wireframe types cover 80% of what appears in job postings.

By the end of this module you can produce an annotated wireframe for each of the three canonical eLearning interaction types, applying WCAG constraints from the lo-fi stage and generating a handoff-ready specification document.
Interaction What to wireframe AWJ worked example
Branching scenario Decision node → 2–3 branches → consequence screen → re-entry point. Label feedback type (corrective / elaborative). Hedging-language choice → over-hedged / under-hedged / correct → model answer screen.
Knowledge check Question stem → response options → answer feedback layer → progress indicator. WCAG: keyboard navigable, error state, focus ring. Single-best-answer on metadiscourse markers → highlight correct + explain distractor.
Dashboard / progress Learner state at a glance: modules completed, score, next step, mastery gate. Data density first. TK CoachAI for Talketika: session score, MLLDE gate status ("Measure, Not Decide"), next recommended session.

Lo-fi → hi-fi process (AWJ as the worked example)

  1. Sketch (lo-fi): boxes for content zones, arrows for navigation flow, labels only — no colour, no fonts. Validate the logic, not the look.
  2. Annotate interactions: every element that does something — click target, hover state, keyboard trigger. Label feedback type (corrective, confirmatory, elaborative).
  3. Apply WCAG constraints early: minimum tap target 44×44px, focus order marked, error states labelled, contrast ratio noted. Fixing WCAG at wireframe stage costs zero rework.
  4. Hi-fi pass: apply Ocean Ink tokens (--primary, --accent, --canvas). Fraunces headings, Inter body. The wireframe becomes a spec sheet.
  5. Handoff document: colour tokens (hex + purpose), font sizes, spacing grid, interaction states, WCAG notes. This is the portfolio artefact.
Portfolio move: Export two frames from the AWJ wireframing process — lo-fi and hi-fi — annotated with the design decisions. That two-frame artefact answers "can you wireframe?" in one image.

Module 3 · Usability testing

The AWJ usability test — method and findings

Think-aloud protocol applied to AWJ before final submission. Graded 10/10 at the UPV Master's programme.

Conduct a five-user think-aloud usability test: recruit participants, write task scenarios, record observations, categorise findings by severity, and produce a before/after revision report that closes the WCAG and usability gaps identified.

Think-aloud protocol — five steps

  1. Recruit 5 participants: 5 is the threshold at which 85% of usability issues surface (Nielsen, 1993). For AWJ: peers from the master's programme — same academic writing context as the target learner.
  2. Give the task, not the instructions: "Use the site to find the section on hedging language and complete the first exercise." Never say "click on…"
  3. Record think-aloud observations: note hesitations, wrong clicks, re-reads, and verbal expressions of confusion — exact quotes. These become the finding statements.
  4. Categorise by severity: Critical (blocks task completion) · Major (significant delay) · Minor (cosmetic). AWJ had 0 critical issues post-revision.
  5. Report with before/after: each finding gets: screenshot of the problem → revision applied → rationale. The revision log is the portfolio artefact.
AWJ result: 10/10 · WCAG 2.1 AA compliant · 0 critical usability issues post-revision.

WCAG as a systematic usability audit method

Running a WCAG 2.2 AA audit alongside a think-aloud test surfaces issues that typical usability tests miss: keyboard-only navigation, screen-reader label completeness, focus ring visibility, colour contrast under different display conditions.

For AWJ, every WCAG checkpoint was verified before submission. This is documented evidence of accessibility competence as part of the UX process — not as a separate compliance exercise.

Common gap in portfolios: L&D professionals list "WCAG" as a skill but have no artefact that shows the process — no audit report, no before/after comparison. The AWJ revision log closes that gap with real evidence.

Module 4 · Design systems for L&D

Ocean Ink — building a design system for a learning portfolio

Make visual decisions once; apply them consistently. Reviewers see a coherent designer, not a collection of disconnected experiments.

Document Ocean Ink as a shareable design system artefact: token table, type scale with use cases, one component (button or feedback banner) in light + dark mode, and a paragraph explaining the WCAG rationale behind each choice.

Token architecture

Every colour is a CSS custom property with a defined purpose, a light value, and a dark value. WCAG contrast ratios are pre-measured:

--primary #3B5BD6 · links, active, button fills
--primary-deep #22307C · headings, hero bands (light)
--accent #E8A33D · gold, single CTAs, labels
--canvas (light) #F7F8FC
--canvas (dark) #0F1120

Type scale — Fraunces + Inter + IBM Plex Mono

  • Fraunces 600–700 — display, H1–H2. Optical-size variable font. Carries the senior, editorial register.
  • Inter 400–600 — body, UI, H3, kicker labels. Chosen for readability at small sizes on screen — a deliberate legibility decision, not "generic sans".
  • IBM Plex Mono 400–500 — code, timestamps, metadata labels. Signals precision without monospace overuse.

Applying Ocean Ink to TK CoachAI for Talketika
